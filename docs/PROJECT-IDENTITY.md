# PROJECT IDENTITY

## 1. DOCUMENT PURPOSE

This document defines the official identity and naming information of the project.

It exists separately from the product, architecture, technical, module, industry, and development specifications so that the project can be renamed without requiring changes to the underlying system architecture or business requirements.

Until an official project name is approved, all technical development must remain project-name neutral.

# 13. NAMING RULES

The following rules are mandatory.

### 13.1 No invented project name

Do not create or assume a project name that has not been officially approved.

### 13.2 No previous project names

Names belonging to previous, unrelated, or abandoned projects must not be reused for this project.

### 13.3 No accidental branding

Temporary development labels must not be presented as the official product name.

### 13.4 Technical neutrality

The architecture, database, API, module system, industry system, authorization system, workflow engine, customization engine, and other technical components must not depend on the final brand name.

### 13.5 Rename safely

When the final name is selected, update the relevant identity and branding references without unnecessarily modifying functional architecture.

# 15. FINAL NAME APPROVAL

The project name becomes official only when explicitly approved by the project owner.

An AI agent, developer, designer, or automated process must not declare a name final without explicit approval.

Once approved, the final name should be recorded in this document as the authoritative project identity.

---

# 16. NAME CHANGE PROCEDURE

If the project name is changed in the future:

1. Update this document first.
2. Update official application branding.
3. Update application metadata where required.
4. Update deployment/package metadata where required.
5. Update repository naming if desired.
6. Update documentation references that explicitly require the product name.
7. Update visual branding assets.
8. Search the codebase for obsolete branding references.
9. Verify that functional and technical identifiers were not unintentionally changed.
10. Test the application after branding changes.
11. Do not redesign or restructure the platform merely because its name changed.

---

# 17. BRANDING VS. ARCHITECTURE

Project identity must remain separate from technical architecture.

The following must not depend on the product's marketing name unless there is a deliberate technical reason:

* database architecture
* database entities
* API architecture
* module architecture
* service boundaries
* business rules
* workflow definitions
* permission architecture
* tenant architecture
* industry templates
* customization engine
* reporting engine
* notification system
* integration architecture
* AI architecture
* testing architecture

A name change should therefore be primarily an identity and branding operation rather than an architectural operation.
